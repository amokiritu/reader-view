Five Small Scripts Worth Keeping

Test Author · 6 min read

Shell scripts are the duct tape of software teams. They glue together builds, deployments and the small chores nobody wants to do by hand, and they tend to live far longer than anyone expects when they are first written.

In this walkthrough we look at a handful of small, real examples. Each one shows a pattern worth keeping, from rewriting commit authors to adding SSH keys, and we finish with a tiny Python and JavaScript helper.

None of these snippets is clever. That is the point: the code you will maintain for years should be boring, obvious and easy to copy into a terminal when you need it at two in the morning.

Before running anything, read it. A script that rewrites history or touches your keys deserves a second look, and the few minutes it takes are cheaper than recovering a broken repository.

With that said, here is the first example, written directly in the article as a code block rather than embedded from GitHub, the way Medium shows code typed into the editor.

import os

def main():
    path = os.getcwd()
    print(f"Working in {path}")

if __name__ == "__main__":
    main()

The second example comes from a GitHub Gist. Medium shows Gists inside a frame that points at its own media pages, which is why most reader modes lose them entirely.

Here is another Gist further down the page. The site loads this frame only when you scroll to it, so Reader has to fetch the code itself, straight from GitHub.

Medium wraps videos the same way, through its media pages and an Embedly player. This one is the very first video ever uploaded to YouTube.

Personal blogs usually embed Gists with GitHub's script tag instead, which draws the code right into the page. Reader should treat both the same way.

Documentation sites often use Pygments, which puts line numbers in a separate column. Copying should give you only the code, never the numbers.

1
2
3
set -euo pipefail
BRANCH=$(git rev-parse --abbrev-ref HEAD)
echo "On $BRANCH"

Prism adds its own line numbers inside the code element. These are drawn with CSS, so they are not part of the text, but the empty markup still has to go.

const sum = (a, b) => a + b;
console.log(sum(2, 3));

Finally, inline code such as git status or npm test stays inside the sentence where it belongs, with no header or button of its own.

That is all five. Keep them somewhere you can find them, and resist the urge to make them clever. Future you will be grateful for every boring line.
